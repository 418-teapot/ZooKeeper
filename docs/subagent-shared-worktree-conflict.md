> git 工作区中协作时互相回滚对方修改，导致已验收成果丢失。分析根因并给出

## 1. 事件概述

ZooKeeper 采用"编排器 + subagent"架构：编排器（dolphin）将任务委派给
beaver（编码）、lynx（搜索）等 subagent 执行。所有 subagent **共享同一个
git 工作区**。

本次需求是将 `config.toml` 三个配置段（`zoo.validation`、`zoo.context`、
`zoo.logging`）的解析策略统一改为"解析失败不填默认值、失败即跳过"
（let it crash）。需求被拆成多轮委派执行，期间触发了两类工作区混乱，
最终用户将全部修改（含已验证通过的 `zoo.validation` 成果）整体回退。

---

## 2. 事件经过

### 2.1 第一阶段：validation 段完成但未提交

- beaver 完成 `zoo.validation` 去兜底改造，`./check.sh` 与 `./test.sh`
  全部通过（1415 个 TS 测试）。
- 改动停留在**未提交**状态，等待后续 code review。

### 2.2 第二阶段：并行委派引发互相回滚

用户追加 `zoo.context` 与 `zoo.logging` 两段需求后，编排器将工作拆成
两条"泳道"并行委派两个 beaver：

- 泳道 1：logging（`src/utils/logger.ts` + `src/opencode.ts` 的
  `initPluginLogger`）
- 泳道 2：context（`src/opencode.ts` 的 `parseContextConfig` + 下游
  hook/producer）

两个并行 beaver 在共享工作区中通过 `git status` 看到对方的半成品修改，
各自的 scope 纪律（"发现无关修改要 revert、不越界"）使其将对方的工作
判定为"无关修改"并回滚，造成极大混乱。

### 2.3 结果

用户回退了全部修改。已验收的 `zoo.validation` 成果因**从未提交**，
在 git 中无任何副本，无法恢复（仅存于会话上下文中）。

---

## 3. 根因分析

### 3.1 根因一：任务分解违反零文件重叠前提（编排器失误）

并行化的前提是泳道之间**文件集合不相交**。本次两条泳道都要修改
`src/opencode.ts`（`initPluginLogger` 与 `parseContextConfig` 同文件），
本就不满足并行条件，却被并行派发。同一文件被两个 agent 并发编辑，
冲突不可避免。

### 3.2 根因二：共享工作区 + scope 防御本能

即使文件不重叠，并行/串行的 subagent 仍共享工作区。subagent 的通用纪律
包含"保持任务边界、revert 无关修改"，但其 prompt 中没有信息告诉它
工作区里哪些修改是"有关"的（其他泳道或先前任务的合法成果）。于是
`git status` 中的一切陌生改动都被当作回滚对象。

**判断权错位**：某个修改是否"无关"，应由掌握全局任务图的编排器判断，
子 agent 没有足够上下文做此判断，但它有执行回滚的能力。

### 3.3 根因三：未提交的修改不受 git 保护

`zoo.validation` 成果验收通过后未提交。未提交状态的工作区修改对任何
`git checkout -- .`、`git restore`、手动回退都毫无抵抗力，且丢失后
git 层面不可恢复。这是损失扩大到已验收成果的直接原因。

## 4. 防护手段对比

| 手段 | 机制 | 可靠性 | 成本 | 局限 |
|------|------|--------|------|------|
| **任务间提交** | 每个任务验收后立即 commit，成果进入 git 历史 | 高：任何破坏都可通过 `git diff HEAD` 暴露、`git restore` 恢复 | 低 | 需要用户授权逐任务提交 |
| **Prompt 显式声明** | 在每个后续任务的 CONTEXT 中列出"先前任务已验收的文件清单，禁止修改/revert；git status 中看到属预期"；并禁止子 agent 执行改变工作区的 git 命令（restore/checkout/reset/clean/stash） | 中：依赖模型遵从 | 极低 | 无强制力，模型可能违反 |
| **编排器基线快照** | 每个任务验收后 `git diff > baseline-N.patch` 存档；下个任务返回后对比基线，既有文件的回滚视为验收失败；被破坏时 `git apply` 还原 | 中高：检测确定性强，恢复可靠 | 低 | 检测发生在破坏之后 |
| **文件范围隔离** | 分解任务时保证各任务文件集合不相交 | 预防性：消除"正当"触碰理由 | 无额外成本 | 无法满足时（共享文件）必须串行 |
| **git worktree 隔离** | 每个并行泳道独立工作区 + 分支，编排器事后合并 | 高：物理隔离 | 高：合并成本、环境同步 | 仅值得用于大改动并行 |

关键结论：

- **唯一能让成果"不可丢失"的手段是提交**。其余手段都是缓解。
- 并行的必要条件是**零文件重叠**；不满足时一律串行，不得强行并行。
- 子 agent 不应拥有"判断哪些修改无关并回滚"的权力；该判断收归编排器。

## 5. 推荐协议

### 5.1 串行多任务（默认场景）

1. 每个任务验收（lint + test + 编排器读码）通过后**立即提交**
   （ZooKeeper 仓库内走 git-commit skill）。
2. 若用户不授权逐任务提交，降级为：验收后编排器立即
   `git diff > /tmp/zoo-baseline-N.patch` 存档。
3. 每个后续任务的 prompt 必须携带声明：
   > 工作区存在先前任务已验收的修改（文件 A、B），属本需求既有成果，
   > 禁止修改或 revert；`git status` 中看到它们是预期。禁止执行任何
   > 改变工作区状态的 git 命令（restore/checkout/reset/clean/stash）。
4. 任务返回后编排器对比基线：既有文件清单不得出现在新 diff 的
   回滚侧；违反则拒绝验收并用快照还原、重新生成任务。

### 5.2 并行多任务（仅当满足全部前提）

前提（缺一不可）：

- 各泳道文件集合**两两不相交**（派发前逐一核对，含测试文件）；
- 每个泳道 prompt 显式声明其他泳道的文件清单及上述禁令；
- 各泳道使用**各自独立**的 subagent 会话。

任一前提不满足 → 串行。大改动且确需并行时，升级为 git worktree
物理隔离，编排器负责合并。

## 6. 关联问题：task_id 跨 agent 类型复用

本次会话同时暴露了会话管理错误：编排器沿用了 lynx 探索任务的
`task_id` 派发 beaver 实现任务，导致不同类型 subagent 的上下文混入
同一会话。

修正规则：

- `task_id` 复用**仅适用于同一 subagent 的会话延续**（重试、补充
  上下文后继续同一任务）；
- 跨 agent 类型（lynx → beaver、eagle 等）派发必须开新会话；
- 并行的同类型任务（两个 beaver 泳道）也应各自独立会话，避免
  上下文串扰。

## 7. 经验教训总结

1. **并行前先核对文件清单**。"看起来是两条独立需求"不等于"文件不
   重叠"——本次两条泳道在 `src/opencode.ts` 交汇，是最常见的陷阱
   （配置解析函数集中在同一入口文件）。
2. **验收通过 ≠ 成果安全**。只有进入 git 历史的成果才真正安全；
   长链条多任务中，"最后一起提交"的策略把每个中间成果都暴露在
   后续所有 subagent 的破坏半径内。
3. **subagent 的纪律需要上下文喂养**。"revert 无关修改"的本能本身
   合理，缺的是"哪些修改有关"的信息；prompt 声明是低成本高回报的
   对齐手段。
4. **破坏判断权收归编排器**。子 agent 只被授权修改指派文件；任何
   越界修改由编排器在验收阶段检测并处理，而不是依赖子 agent
   自行"清理现场"。
5. **损失会沿链条放大**。第二阶段的并行混乱不仅毁了当期工作，
   还连带夺走了第一阶段已验收的成果——单点流程缺陷在多任务链条
   中会复合放大。
